# DevOps Demo: nginx + Flask + MySQL в Docker

Мини-проект для тренировки: nginx как reverse proxy принимает весь
внешний трафик, Flask-приложение читает текст из MySQL и отдаёт его
на веб-странице. Наружу торчит только nginx — контейнеры `web` и `db`
недоступны с хоста напрямую.

## Архитектура

```
                 хост-машина
                      │
                 порт 8080
                      │
                      ▼
            ┌───────────────────┐
            │   nginx (image)   │   ← единственный "вход" снаружи
            └─────────┬─────────┘
                       │  внутренняя docker-сеть
                       ▼
            ┌───────────────────┐
            │  web (Dockerfile) │   ← порт 5000 не публикуется на хост
            └─────────┬─────────┘
                       │
                       ▼
            ┌───────────────────┐
            │   db (image)      │   ← порт 3306 не публикуется на хост
            └───────────────────┘
```

Клиент видит только nginx на порту 8080. Порты `web` (5000) и `db` (3306)
объявлены через `expose`, а не `ports` — это значит, что они доступны
другим контейнерам в той же docker-сети по имени сервиса, но не
проброшены на хост и недоступны снаружи вообще.

## Структура проекта

```
devops-demo/
├── app.py                        # Flask-приложение
├── requirements.txt              # Python-зависимости
├── Dockerfile                     # Сборка образа приложения (web)
├── docker-compose.yml             # Prod-конфигурация: nginx + web + db + backup
├── docker-compose.override.yml     # Dev-надстройка: hot-reload, прямой доступ к web
├── nginx/
│   └── nginx.conf                   # Конфиг reverse proxy
├── backup/
│   ├── Dockerfile                    # Контейнер для бэкапов (mysql-client + cron)
│   ├── entrypoint.sh                  # Прокидывает env в cron, запускает планировщик
│   └── backup.sh                      # Сам скрипт mysqldump + ротация
├── backups/                        # Сюда падают .sql.gz (в .gitignore, см. ниже)
├── .env.example                      # Пример переменных окружения
└── .dockerignore
```

## Запуск

1. Скопируйте `.env.example` в `.env` и при желании поменяйте пароли:
   ```bash
   cp .env.example .env
   ```

2. Соберите и запустите контейнеры:
   ```bash
   docker compose up --build
   ```

3. Откройте в браузере:
   ```
   http://localhost:8080
   ```
   (не 5000 — этот порт больше не проброшен на хост)

4. Проверить, что контейнеры живы:
   ```bash
   docker compose ps
   ```

5. Убедиться, что порты действительно скрыты — попытка достучаться
   напрямую до web или db с хоста должна упасть:
   ```bash
   curl http://localhost:5000    # Connection refused
   mysql -h 127.0.0.1 -P 3306    # Connection refused
   ```

6. Остановить всё:
   ```bash
   docker compose down
   ```
   Чтобы ещё и удалить данные MySQL (volume):
   ```bash
   docker compose down -v
   ```

## Как это устроено (для понимания, не только для запуска)

- **nginx** — официальный образ `nginx:1.27-alpine`, конфиг
  подключается volume'ом из `nginx/nginx.conf`. `proxy_pass http://web:5000`
  работает благодаря встроенному DNS docker-compose: имя сервиса `web`
  резолвится в IP контейнера внутри общей сети проекта.
- **web** — собирается локально из `Dockerfile`. `expose: 5000` вместо
  `ports: 5000:5000` — контейнер слушает порт внутри сети, но docker
  не создаёт для него правило проброса на хост.
- **db** — официальный образ `mysql:8.0`, аналогично без `ports`,
  данные лежат в именованном volume `db_data`.
- **depends_on + healthcheck** — `web` стартует только после того, как
  MySQL реально готов принимать подключения, а `nginx` — после старта `web`.
- **retry-логика в app.py** — дополнительная подстраховка на случай,
  если MySQL всё ещё доинициализируется после прохождения healthcheck.
- Пароли и хост БД не зашиты в код — берутся из переменных окружения
  через `.env` файл.

### Важный нюанс про "скрытые" порты

`expose` в compose — это, по сути, просто документация для читающего
файл человека: docker-контейнеры в одной user-defined сети и так видят
друг друга по всем портам, независимо от `expose`. Реальная изоляция
от внешнего мира достигается тем, что для `web` и `db` **нет секции
`ports`** — именно она создаёт правило `iptables`/проброс с хоста
в контейнер. Если бы вы оставили `ports: "5000:5000"` у `web`, nginx
всё равно работал бы, но и напрямую на 5000 порт можно было бы
достучаться с хоста в обход прокси.

## Dev vs Prod режим

Проект специально разделён на два файла:

- **`docker-compose.yml`** — базовый, безопасный "prod-подобный" конфиг:
  `web` и `db` не торчат на хост, код зашит внутрь образа на момент сборки,
  debug-режим Flask выключен.
- **`docker-compose.override.yml`** — dev-надстройка. Compose подхватывает
  её **автоматически**, если она лежит рядом и вы просто пишете
  `docker compose up` — ничего дополнительно указывать не нужно.

### Что меняет override для dev

```bash
docker compose up --build
```
Compose смержит оба файла. В результате для `web`:
- подключается bind-mount `./:/app` — папка проекта с хоста монтируется
  поверх того, что `COPY`-нуто в образ. Меняете `app.py` на хосте — Flask
  (благодаря `FLASK_DEBUG=1` и встроенному reloader'у) сам перезапустится,
  ребилдить образ не нужно;
- пробрасывается порт `5000:5000` — можно достучаться до Flask напрямую,
  в обход nginx, и увидеть полный traceback в браузере при ошибке.

### Как запустить именно prod-конфигурацию (без override)

Автоматический merge — это удобно для разработки, но иногда нужно
явно проверить "чистый" prod-вариант, каким его увидит сервер:

```bash
docker compose -f docker-compose.yml up --build
```

Флаг `-f docker-compose.yml` говорит compose использовать **только**
этот файл и не подхватывать `override.yml` автоматически. В этом
режиме `web` снова без bind-mount и без проброшенного 5000 порта —
доступ строго через `http://localhost:8080` (nginx), как и должно
быть на реальном сервере.

### Почему `debug=True` не должен быть зашит в код

Раньше в `app.py` было `app.run(debug=True, ...)` намертво в коде.
Это плохая практика для прода по двум причинам:
1. При ошибке Flask показывает пользователю полный traceback —
   это может слить куски кода, пути на сервере, переменные окружения.
2. Встроенный debugger Werkzeug (который включается вместе с `debug=True`)
   имеет консоль, позволяющую **выполнять произвольный Python-код** —
   если он случайно окажется доступен извне, это критическая уязвимость.

Теперь `debug` читается из переменной окружения `FLASK_DEBUG`,
которая явно включена только в dev-override и отсутствует в prod-файле.

## Бэкапы базы данных

Named volume `db_data` — это НЕ бэкап, это просто хранилище MySQL.
`docker compose down -v` или падение диска уничтожит его вместе с данными.
Отдельный сервис `backup` регулярно снимает дамп и кладёт его на хост,
в папку `./backups` — вне docker volume, так что она переживёт даже
полное удаление контейнеров и volume'ов.

### Как это устроено

- Образ `backup` собран на базе `mysql:8.0` (в нём уже есть `mysqldump`),
  сверху доустановлены `cron` и `gzip` — ровно тот случай "настроить
  окружение по-своему", про который вы спрашивали в прошлый раз.
- `entrypoint.sh` сохраняет переменные окружения в `/etc/environment`,
  потому что cron по умолчанию их не видит (частая засада: скрипт
  работает при ручном запуске и падает по расписанию из-за отсутствия env).
- По расписанию (`0 3 * * *` — каждый день в 03:00) запускается
  `backup.sh`: `mysqldump --single-transaction` → `gzip` → файл с
  таймстампом в `/backups`, что через volume смонтировано в `./backups`
  на хосте.
- Бэкапы старше `BACKUP_RETENTION_DAYS` (по умолчанию 7 дней) удаляются
  автоматически при каждом запуске — чтобы диск не забился.

### Запустить бэкап руками (не дожидаясь 03:00)

```bash
docker compose exec backup /backup/backup.sh
ls -lh backups/
```

### Восстановить из бэкапа

```bash
gunzip < backups/demo_db_2026-09-10_03-00-00.sql.gz | \
  docker compose exec -T db mysql -u root -p"$MYSQL_ROOT_PASSWORD" demo_db
```

### Добавьте в `.gitignore`

Сами дампы в репозиторий коммитить не нужно (там реальные данные
и потенциально чувствительная информация):
```
backups/*.sql.gz
```

## Автоматические рестарты

У всех сервисов уже стоит `restart: unless-stopped`. Разница между
политиками restart в Docker:

| Политика | Перезапускает при крэше | Перезапускает после `docker stop` + `reboot` хоста | Перезапускает после ручного `docker stop` (без reboot) |
|---|---|---|---|
| `no` (по умолчанию) | ❌ | ❌ | ❌ |
| `on-failure` | ✅ (только если exit code ≠ 0) | ✅ | ❌ |
| `unless-stopped` | ✅ | ✅ | ❌ |
| `always` | ✅ | ✅ | ✅ |

Мы используем `unless-stopped` — если контейнер упал или хост
перезагрузился, он поднимется сам; но если вы намеренно остановили его
командой `docker stop`, он не влезет обратно после `reboot`, пока
не скажете `docker compose up` явно. Это разумный дефолт для большинства
проектов.

Здесь важны два момента, без которых `restart` не сработает как ожидаете:
1. **Docker daemon должен стартовать при загрузке хоста**:
   ```bash
   sudo systemctl enable docker
   ```
   Без этого `unless-stopped`/`always` бесполезны после `reboot` — если
   сам демон не поднялся, поднимать нечего.
2. **Healthcheck — это не то же самое, что restart policy.** Docker сам
   по себе не перезапускает контейнер только потому, что healthcheck
   вернул `unhealthy` — он лишь помечает статус (это видно в `docker compose ps`)
   и влияет на `depends_on: condition: service_healthy` у других сервисов.
   Поэтому мы добавили healthcheck и `web`, и `nginx` — теперь `nginx`
   действительно ждёт, пока Flask не просто запустится, а начнёт отвечать
   на `/health`, а не просто "процесс стартовал".

Для по-настоящему автоматического рестарта именно по healthcheck (а не
только по крэшу процесса) на одном хосте обычно используют
`docker-autoheal` (контейнер, слушающий Docker socket и перезапускающий
`unhealthy` контейнеры) — либо, если проект вырастет, переезжают на
Docker Swarm/Kubernetes, где это встроено в оркестратор по умолчанию.

## Нужен ли fail2ban?

Короткий ответ: **fail2ban — не PHP-специфичная вещь**, он одинаково
применим к любому бэкенду. Но для конкретно этого учебного проекта
он не первое, что стоит добавлять. Разберу почему.

**Что такое fail2ban на самом деле.** Это демон, который живёт на
хосте, читает лог-файлы (SSH, nginx access/error log, postfix и т.д.),
ищет паттерны вроде "10 неудачных попыток логина за минуту с одного IP",
и банит этот IP через iptables на N минут/часов. Он не привязан к языку
бэкенда — просто исторически чаще всего упоминается вместе с PHP/WordPress,
потому что это самый массово сканируемый ботами софт в интернете
(`wp-login.php`, `xmlrpc.php`, `phpmyadmin` — открой любой публичный
сервер, и в логах через 10 минут будут попытки достучаться именно туда).

**Почему для этого проекта сейчас не критично:**
- У нас нет страницы логина — банить по неудачным попыткам входа нечего.
- Проект учебный и не смотрит в реальный интернет.

**Когда стало бы актуально:**
- Как только вы добавите что-то с логином (админку, API с авторизацией) —
  боты будут долбить `/login` перебором независимо от того, что у вас
  под капотом: Flask, Django, PHP, Node — не важно.
- Даже без логина боты сканируют пути на удачу: `/.env`, `/.git/config`,
  `/wp-admin` (даже если у вас не WordPress — сканируют всех подряд).
  От этого fail2ban тоже помогает — есть готовые jail'ы под nginx,
  которые банят по количеству 404 за короткое время.

**Важный нюанс именно с docker.** fail2ban банит через iptables, а
Docker сам активно управляет iptables для проброса портов (`ports:`
в compose создаёт DNAT-правила). Правила fail2ban по умолчанию иногда
**не успевают сработать раньше**, чем сработает NAT от Docker — это
известная и частая засада, для правильной работы бан нужно вставлять
в цепочку `DOCKER-USER`, а не в стандартную `INPUT`. Это отдельная
настройка, не "из коробки".

**Что я бы предложил вместо fail2ban для нашего конкретного стека** —
`limit_req` прямо в nginx. Это встроенный модуль, не требует доступа
к хосту и iptables, работает просто как часть конфига:

```nginx
limit_req_zone $binary_remote_addr zone=basic:10m rate=10r/s;

server {
    location / {
        limit_req zone=basic burst=20 nodelay;
        proxy_pass http://web:5000;
        ...
    }
}
```

Это не полная замена fail2ban (fail2ban банит надолго и по более умным
паттернам, а `limit_req` просто троттлит скорость запросов), но для
контейнеризированного стека это гораздо проще внедрить и без граблей
с iptables-цепочками. На реальном проде часто используют оба: fail2ban
на уровне хоста для SSH и общей защиты, plus rate-limiting в nginx для
HTTP-уровня.

Если хотите, в следующий раз можем добавить `limit_req` в наш `nginx.conf` —
займёт 5 минут и хорошо ляжет в резюме/на собеседовании как "понимаю
разницу между rate-limiting на уровне приложения и intrusion prevention
на уровне хоста".

## Что можно потренировать дальше

- Добавить `adminer` или `phpmyadmin` сервис для просмотра БД в браузере
  (тоже без публикации портов наружу — доступ только через nginx-location).
- Настроить TLS в nginx (самоподписанный сертификат для тренировки HTTPS).
- Вынести конфиг в `docker-compose.override.yml` для dev/prod окружений.
- Настроить multi-stage build в Dockerfile, чтобы уменьшить размер образа.
- Добавить `.github/workflows` для CI, который собирает образ при пуше.
- Добавить `docker network` явно с именем, вместо дефолтной сети compose.
